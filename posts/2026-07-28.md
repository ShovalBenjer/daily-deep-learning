## עיון: N-Step Returns ו-GAE - ספקטרום ה-Bias-Variance

### פתיחה מאפס

אתמול בנינו Actor-Critic עם **TD error, שגיאת TD**: \(\delta_t = r_t + \gamma V_\phi(s_{t+1}) - V_\phi(s_t)\). זה עדכון חד-צעדי: רואים tuple אחד \((s_t, a_t, r_t, s_{t+1})\) ומיד מעדכנים. אבל מה קורה כש-reward המשמעותי מגיע ב-\(t+4\) ולא ב-\(t+0\)?

**N-step return, תשואה n-צעדית**: שילוב של n צעדי reward אמיתי עם bootstrap של ה-Critic מרחוק n:

\[\hat{G}_t^{(n)} = r_t + \gamma r_{t+1} + \gamma^2 r_{t+2} + \ldots + \gamma^{n-1} r_{t+n-1} + \gamma^n V_\phi(s_{t+n})\]

כש-\(n=1\): בדיוק ה-1-step TD של אתמול. כש-\(n \to \infty\): Monte Carlo (ה-\(V_\phi\) נעלם, נשאר \(G_t\) מלא).

**Bias, הטיה**: שגיאה שיטתית שלא נעלמת עם עוד דגימות. כש-\(V_\phi\) מוטה (בתחילת אימון, תמיד), ה-1-step TD יורש את הטיה. n גדול = פחות הסתמכות על \(V_\phi\) = פחות הטיה.

**Variance, שונות**: פיזור התוצאות סביב הממוצע. Monte Carlo מסתמך על trajectories שלמות - כל מסלול שונה = שונות גבוהה. n קטן = פחות מסלול = פחות שונות.

**Lambda return, תשואת-\(\lambda\)**: ממוצע משוקלל גיאומטרי של כל n-step returns:

\[\hat{G}_t^\lambda = (1-\lambda)\sum_{n=1}^{\infty} \lambda^{n-1} \hat{G}_t^{(n)}\]

כש-\(\lambda=0\): הסכום כולו הוא המשקל על \(n=1\). כש-\(\lambda=1\): Monte Carlo.

**GAE (Generalized Advantage Estimation), אומדן יתרון מוכלל**: הנוסחה של Schulman et al. 2015, שמחשבת:

\[\hat{A}_t^{GAE(\gamma,\lambda)} = \sum_{k=0}^{\infty} (\gamma\lambda)^k \delta_{t+k}\]

שקולה ל-lambda return של advantages. ניתנת לחישוב לאחור ב-\(O(T)\).

**Eligibility trace, עקבת זכאות**: מנגנון שמוסיף לכל פרמטר "זיכרון" של מה שתרם לצעדים האחרונים. \(e_t = \gamma\lambda e_{t-1} + \nabla_\theta \log\pi(a_t|s_t)\). GAE כבוחן-advantage הוא מקבילת הצד הביקורתי.

### האינטואיציה

תחשבו על שחקן שח שמנסה להעריך עד כמה צעד מסוים היה טוב.

**גישת TD (n=1):** מסתכלים רק על הצעד הבא: "האם המצע שנוצר לאחר הצעד שלי אמר שהייתי בסיטואציה טובה?" מהיר, אבל ה-Critic שמעריך "כמה טוב המצב" עלול להיות מוטה - בייחוד בתחילת אימון.

**גישת Monte Carlo (n=\infty):** מחכים עד סוף המשחק ואז מסתכלים אחורה: "עד כמה הצעד שלי תרם לתוצאה הסופית?" מדויק (כי רואים את כל ה-reward בפועל), אבל שונות גבוהה - כל מסלול שונה עלול לתת תמונה שונה.

**גישת GAE:** "בוא נסתכל n צעדים קדימה - לא אחד, לא עד הסוף - ונשקלל את כל האפשרויות עם דיכוי exponential." ה-\(\lambda\) שולט על הטריידאוף.

**הנקודה הקריטית:** ה-attenuation factor הוא \(\gamma\lambda\), לא \(\lambda\) לבד. אם \(\gamma=0.99\) ו-\(\lambda=0.95\): \(\gamma\lambda = 0.94\). TD error שמגיע 10 צעדים אחר כך מוכפל ב-\(0.94^{10} = 0.54\) - עדיין חצי ממשקלו. זה PPO: \(\lambda=0.95\) נותן מבט עמוק אבל מוגבל.

### הפורמליזם המלא

#### שלב 1: n-step advantage כסכום של TD errors

ה-n-step advantage: \(\hat{A}_t^{(n)} = \hat{G}_t^{(n)} - V_\phi(s_t)\).

**הטענה:** \(\hat{A}_t^{(n)} = \sum_{k=0}^{n-1} \gamma^k \delta_{t+k}\)

**הוכחה בגרירה (telescoping):**

\begin{align}
\delta_t &= r_t + \gamma V(s_{t+1}) - V(s_t) \\
\gamma\delta_{t+1} &= \gamma r_{t+1} + \gamma^2 V(s_{t+2}) - \gamma V(s_{t+1}) \\
\gamma^2\delta_{t+2} &= \gamma^2 r_{t+2} + \gamma^3 V(s_{t+3}) - \gamma^2 V(s_{t+2}) \\
\vdots & \\
\gamma^{n-1}\delta_{t+n-1} &= \gamma^{n-1} r_{t+n-1} + \gamma^n V(s_{t+n}) - \gamma^{n-1} V(s_{t+n-1})
\end{align}

מסכמים: כל ה-\(V\) הפנימיים מצטמצמים זוגיות (telescoping). נשאר:

\[\sum_{k=0}^{n-1}\gamma^k\delta_{t+k} = r_t + \gamma r_{t+1} + \ldots + \gamma^{n-1}r_{t+n-1} + \gamma^n V(s_{t+n}) - V(s_t) = \hat{A}_t^{(n)}\]

#### שלב 2: GAE כ-lambda-weighted sum

\[\hat{A}_t^{GAE} = (1-\lambda)\sum_{n=1}^{\infty}\lambda^{n-1}\hat{A}_t^{(n)} = (1-\lambda)\sum_{n=1}^{\infty}\lambda^{n-1}\sum_{k=0}^{n-1}\gamma^k\delta_{t+k}\]

מחלפים סדר סכימה: עבור \(\delta_{t+k}\), הוא תורם לכל \(n > k\), ומקבל משקל \((1-\lambda)\sum_{n=k+1}^{\infty}\lambda^{n-1} = (1-\lambda)\cdot\frac{\lambda^k}{1-\lambda} = \lambda^k\). לכן:

\[\hat{A}_t^{GAE} = \sum_{k=0}^{\infty}(\gamma\lambda)^k\delta_{t+k}\]

#### שלב 3: recurrence לאחור ב-O(T)

\[\hat{A}_T^{GAE} = \delta_T \quad\text{(terminal: אין הבא)}\]
\[\hat{A}_t^{GAE} = \delta_t + (\gamma\lambda)\hat{A}_{t+1}^{GAE}\]

**בדיוק כמו:** \(\hat{G}_t^\lambda = r_t + \gamma\hat{G}_{t+1}^\lambda\) אבל עם TD errors במקום rewards. מחשבים לאחור על trajectory שלם ב-\(O(T)\).

#### שלב 4: Actor update עם GAE

\[\nabla_\theta J(\theta) \approx \frac{1}{T}\sum_{t=0}^{T-1}\hat{A}_t^{GAE}\cdot\nabla_\theta\log\pi_\theta(a_t|s_t)\]

זהה לאתמול, אבל \(\hat{A}_t^{GAE}\) במקום \(\delta_t\). ה-Critic ממשיך להתאמן כרגיל (MSE על TD targets), GAE שינה רק את האות לשחקן.

### דוגמה מחושבת ביד

**Trajectory:** 5 צעדים, \(\gamma=0.9\), \(\lambda=0.5\).

```
t:       0     1     2     3     4     (terminal)
r:       1.0   0.0   3.0   0.0   5.0
V(s_t):  2.0   1.5   3.0   2.0   0.0
V(s_5):  0.0   (terminal)
```

**שלב 1: חשב \(\delta_t\) לכל t**

\[\delta_4 = 5.0 + 0.9 \times 0.0 - 0.0 = 5.0\]
\[\delta_3 = 0.0 + 0.9 \times 0.0 - 2.0 = -2.0\]
\[\delta_2 = 3.0 + 0.9 \times 2.0 - 3.0 = 3.0 + 1.8 - 3.0 = 1.8\]
\[\delta_1 = 0.0 + 0.9 \times 3.0 - 1.5 = 2.7 - 1.5 = 1.2\]
\[\delta_0 = 1.0 + 0.9 \times 1.5 - 2.0 = 1.0 + 1.35 - 2.0 = 0.35\]

**שלב 2: GAE לאחור** (\(\gamma\lambda = 0.9 \times 0.5 = 0.45\))

\[\hat{A}_4^{GAE} = \delta_4 = 5.0\]
\[\hat{A}_3^{GAE} = \delta_3 + 0.45 \times \hat{A}_4^{GAE} = -2.0 + 0.45 \times 5.0 = -2.0 + 2.25 = 0.25\]
\[\hat{A}_2^{GAE} = \delta_2 + 0.45 \times \hat{A}_3^{GAE} = 1.8 + 0.45 \times 0.25 = 1.8 + 0.1125 = 1.9125\]
\[\hat{A}_1^{GAE} = \delta_1 + 0.45 \times \hat{A}_2^{GAE} = 1.2 + 0.45 \times 1.9125 = 1.2 + 0.8606 = 2.0606\]
\[\hat{A}_0^{GAE} = \delta_0 + 0.45 \times \hat{A}_1^{GAE} = 0.35 + 0.45 \times 2.0606 = 0.35 + 0.9273 = 1.2773\]

**מה לומדים:**
- \(\hat{A}_4 = 5.0\): ה-reward הגדול ב-t=4 מוערך גבוה.
- \(\hat{A}_3 = 0.25\): ה-\(\delta_3\) השלילי (\(-2.0\)) מקוזז על ידי ה-advantage שמגיע מ-t=4. ה-0.45 factor מגביל כמה "עתיד" מגיע.
- \(\hat{A}_0 = 1.28\): מוגבל ביחס ל-\(\hat{A}_4 = 5.0\) בגלל \(0.45^4 = 0.041\). ה-reward הגדול ב-t=4 כמעט לא מגיע ל-t=0.

### דוגמה שנייה: מה קורה כש-\(\lambda \to 1\)

עם אותו trajectory, \(\lambda=0.99\), \(\gamma\lambda = 0.9 \times 0.99 = 0.891\):

\[\hat{A}_0^{GAE}(\lambda=0.99) = \delta_0 + 0.891\delta_1 + 0.891^2\delta_2 + 0.891^3\delta_3 + 0.891^4\delta_4\]
\[= 0.35 + 0.891(1.2) + 0.794(1.8) + 0.708(-2.0) + 0.631(5.0)\]
\[= 0.35 + 1.069 + 1.429 - 1.416 + 3.155 = 4.587\]

לעומת \(\lambda=0.5\): \(\hat{A}_0 = 1.277\).

**הפרש עצום.** כש-\(\lambda\) גדול, ה-reward הגדול ב-t=4 "מגיע" בעצמה גדולה ל-t=0. זה מדויק יותר (כי reward=5 אמיתי), אבל שונות גבוהה יותר - trajectory אחר עם r=0 ב-t=4 ייתן advantage שלילי ב-t=0.

**ה-edge case:** כש-\(\gamma\lambda = 1\) (\(\gamma=\lambda=1\)): כל \(\delta\) מקבל משקל שווה. GAE = \(\hat{A}_t^{MC} = G_t - V(s_t)\). שונות בלתי חסומה - כל trajectory שלם משפיע ב-100%.

### טעויות נפוצות

**1. שכחת לאפס GAE בגבול ה-episode:** כש-done=True ב-t=T, אין episode הבא. חייב: \(\hat{A}_T = \delta_T\) ולא \(\hat{A}_T = \delta_T + \gamma\lambda\hat{A}_{T+1}\) מה-episode הבא. הדרך הנפוצה: `last_adv = 0.0` לפני הלולאה, וכש-`done=True`: `last_adv = 0.0` לפני `last_adv = delta + gamma*lam*last_adv`.

**2. לכתוב \(\gamma\lambda\) כ-\(\lambda\) בקוד:** ה-attenuation factor ב-recurrence הוא `gamma * lam`, לא `lam` לבד. שגיאה שכיחה: `adv = delta + lam * next_adv`. הנכון: `adv = delta + gamma * lam * next_adv`. ב-\(\gamma=0.99, \lambda=0.97\): ההבדל בין `0.97` ל-`0.9603` מצטבר ל-5 צעדים להבדל של 15%.

**3. לא לנרמל advantages לפני עדכון ה-Actor:** GAE מחזיר ערכים בסקאלה של ה-reward. ב-PPO: `A_norm = (A - mean(A)) / (std(A) + 1e-8)`. בלי נרמול, learning rate שמתאים ל-rewards בטווח [0,1] גורם ל-divergence על rewards בטווח [0,100].

**4. להשתמש ב-GAE כ-Critic target ישירות:** ה-Critic target הוא \(\hat{V}_t = \hat{A}_t^{GAE} + V_\phi(s_t)\) (advantage + current value estimate). שגיאה: להשתמש ב-\(\hat{A}_t^{GAE}\) ישירות כ-target. ה-Critic ינסה ללמוד את ה-advantage (שעוגן סביב אפס) במקום את ה-value function.

**5. לחשב GAE קדימה ולא לאחור:** הנוסחה \(\sum_k (\gamma\lambda)^k\delta_{t+k}\) נראית כצבירה קדימה, אבל חישוב ישיר הוא \(O(T^2)\). ה-recurrence לאחור הוא \(O(T)\) ומחשב את אותה תוצאה.

### מתי לא

**GAE אינו תמיד הבחירה הנכונה:**

- **Off-policy methods (DQN, SAC):** GAE מניח on-policy. הניסיון מ-replay buffer = מדיניות ישנות. advantage מחושב על-ידי מדיניות ישנה ביחס ל-Critic נוכחי = bias מובנה. DQN משתמש ב-1-step TD ישירות.
- **Environments עם episodes קצרים (3-10 צעדים):** ה-Monte Carlo return (\(\lambda=1\)) הוא exact ולא יקר. GAE מוסיף hyperparameter (\(\lambda\)) שצריך כוונון ללא תועלת.

**חלופה ראשית:** 1-step Actor-Critic (אתמול). פשוט יותר, Critic אחד, עדכון online. בחרו בו כש-episodes קצרים, Critic מכויל היטב, או off-policy. GAE הכרחי ב-PPO כי הוא עושה multiple epochs על rollout שנאסף - ה-\(\lambda\) מספק enough signal לכל epoch.

**רמז:** ב-recurrence \(\hat{A}_t = \delta_t + \gamma\lambda\hat{A}_{t+1}\), ה-\(\hat{A}_{t+1}\) צריך להיות מוכן לפני שמחשבים \(\hat{A}_t\). חישוב לאחור מבטיח זאת.

**פתרון:**

```python
def compute_gae(rewards: list, values: list, gamma: float, lam: float) -> list:
    T = len(rewards)
    advantages = [0.0] * T
    last_adv = 0.0

    for t in reversed(range(T)):
        delta = rewards[t] + gamma * values[t + 1] - values[t]
        last_adv = delta + gamma * lam * last_adv
        advantages[t] = last_adv

    return advantages
```

### חלק ב: SQL Window Function על MatchIQ (resume-risk: sql)

**הקשר:** MatchIQ שומרת events לכל משחק. נרצה לחשב את ה-cumulative xG (expected goals) שנצבר עד כל אירוע, בתוך כל משחק בנפרד.

**הטבלה:**

```sql
-- match_events (match_id INT, event_id INT, event_time INT, xg FLOAT)
-- (1, 1, 5, 0.12), (1, 2, 23, 0.05), (1, 3, 67, 0.31)
-- (2, 4, 12, 0.08), (2, 5, 55, 0.22)
```

**המשימה:** כתבו שאילתה שמחזירה match_id, event_id, event_time, xg, ו-cumulative_xg (צבירה רצה בתוך כל משחק, ממוין לפי event_time).

<details>
<summary>רמז, ואז פתרון</summary>

**רמז:** `SUM(xg) OVER (PARTITION BY match_id ORDER BY event_time ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`

**פתרון:**

```sql
SELECT
    match_id,
    event_id,
    event_time,
    xg,
    SUM(xg) OVER (
        PARTITION BY match_id
        ORDER BY event_time
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS cumulative_xg
FROM match_events
ORDER BY match_id, event_time;
```

**פלט עבור match_id=1:**

| event_time | xg  | cumulative_xg |
|------------|-----|---------------|
| 5          | 0.12 | 0.12         |
| 23         | 0.05 | 0.17         |
| 67         | 0.31 | 0.48         |

**DataLemur-register:** PARTITION BY מאפס את הצבירה לכל match חדש. ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW מוסיף את השורה הנוכחית (שלא קורה אוטומטית ב-RANGE). `ORDER BY` לבד (ללא ROWS) ייתן אותו תוצאה כאן, אבל ROWS מפורש הוא בטוח יותר עם ties.

</details>

## AI-103: Multi-Agent Orchestration ו-Autonomous-with-Approval

### מה ה-exam צריך

שבוע 2 ממשיך (Generative AI + agentic, 30-35%) עם **Connected Agents** ו-**human-in-the-loop** patterns.

**Connected Agents (סוכנים מחוברים):** Azure AI Agent Service מאפשר ל-orchestrator לקרוא ל-sub-agent כ-tool. ה-interface:

- ה-orchestrator מגדיר agent tool שמצביע ל-sub-agent id.
- כש-orchestrator מחליט לקרוא, ה-Agent Service מריץ את ה-sub-agent עם ה-input.
- ה-sub-agent מחזיר תוצאה ל-orchestrator כ-tool output.
- **כלל לבחינה:** שגיאה ב-sub-agent חוזרת ל-orchestrator כ-tool response (לא failure ישיר); ה-orchestrator מחליט אם לנסות שוב.

**Autonomous-with-Approval Pattern:**

מה שה-exam קורא human-in-the-loop בהקשר agentic:

1. הסוכן מתקדם אוטונומית עד לפעולה בלתי-הפיכה (מחיקה, פרסום, שינוי DB).
2. מחזיר status `required_action` עם function call ל-`confirm_deletion` (דוגמה).
3. ה-client מציג למשתמש ומחכה לאישור.
4. ה-client שולח `submit_tool_outputs` עם `approved=true`.
5. הריצה ממשיכה.

**כלל לבחינה:** `code_interpreter` רץ ב-sandbox של Azure ולא דורש client execution. `function` tool תמיד דורש client execution. זו הנקודה שמאפשרת human-in-the-loop: ה-function "confirm_deletion" מגיע לידי ה-client שיכול לשאול אדם.

**Observability ו-Tracing:**

Azure AI Foundry -> Tracing: כל run מתועד עם:
- `token_usage`: input + output tokens לכל step.
- `tool_calls`: שם הכלי, arguments, response time.
- `latency_breakdown`: TTFT, completion time, tool execution time.

**כלל FinOps:** "cost per answer" = סכום token_usage על פני כל steps של run. agent שצורך פי-10 מהממוצע = runaway loop או context explosion. ה-fix: `max_steps` limit + loop detection בפרומפט של ה-orchestrator.

**Microsoft Learn:** https://learn.microsoft.com/en-us/azure/ai-services/agents/concepts/overview

**Bridge line:** GAE מחלק credit על-פני צעדי מסלול; tracing עושה את אותו הדבר ל-agent run: חושף אילו tool calls תרמו לתוצאה ואילו היו overhead.
