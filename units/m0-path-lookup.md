# PATH ואיך פקודה נמצאת

על המחשב הזה מותקנות שתי גרסאות Python, ורק אחת מהן עונה כשאתה כותב `python`. השנייה לא שבורה. היא פשוט מאוחרת יותר ברשימה.

## מה תדע בסוף

להסביר איך ה-shell מחליט איזה קובץ להריץ כשכתבת שם פקודה, לגלות בפקודה אחת שיש כמה מועמדים, ולדעת למה `pip install` יכול להצליח בזמן ש-`import` נכשל.

## האינטואיציה

בניין עם מסדרון ארוך של דלתות ממוספרות, ובידך רשימה מסודרת של קומות לבדוק בהן.

אתה מבקש "תמצא לי את python". השוער מתחיל בקומה הראשונה שברשימה, עובר על השלטים, וברגע שהוא רואה שלט מתאים הוא פותח את הדלת ומפסיק לחפש. הוא לא ממשיך לקומות הבאות. הוא לא בודק אם יש שם python חדש יותר, גדול יותר או מתאים יותר.

**הראשון ברשימה מנצח, והחיפוש נעצר.** כל התנהגות מפתיעה בנושא הזה נובעת מהמשפט הזה.

## ההגדרות המדויקות

**PATH**: משתנה סביבה שמכיל רשימה **מסודרת** של תיקיות, מופרדות בנקודתיים ב-POSIX ובנקודה-פסיק ב-Windows. הסדר הוא המידע, לא רק התוכן.

**חיפוש הפקודה**: כשכתבת שם בלי לוכסן, ה-shell בודק לפי הסדר הבא:

1. **Alias**, כינוי שהגדרת.
2. **Builtin, פקודה מובנית**: פקודה שממומשת בתוך ה-shell עצמו ואין לה קובץ כלל. `cd` היא כזו, והיא חייבת להיות כזו: תהליך נפרד לא יכול לשנות את התיקייה של ההורה שלו.
3. **PATH**, תיקייה אחר תיקייה לפי הסדר, עד ההתאמה הראשונה.

**שם עם לוכסן** כמו `./script.sh` או `/usr/bin/ls` אינו מופעל דרך PATH כלל. הוא נתיב, וה-shell פונה ישירות אליו. זו הסיבה שצריך `./` כדי להריץ סקריפט בתיקייה הנוכחית: התיקייה הנוכחית אינה ב-PATH, בכוונה, כדי שקובץ בשם `ls` בתיקייה זרה לא ייחטף במקום הפקודה האמיתית.

**`type -a`**: מראה את **כל** המועמדים לפי הסדר. `type` בלי הדגל מראה רק את מי שינצח בפועל.

**Hash table, טבלת מטמון**: bash זוכר איפה מצא כל פקודה כדי לא לחפש שוב. אם התקנת גרסה חדשה במקום מוקדם יותר ב-PATH והיא לא נתפסת, `hash -r` מנקה את הזיכרון הזה.

## המקרה שמפיל את האינטואיציה

`pip install` מצליח, ואז `import` נכשל.

```
type -a pip
```

```
pip is /c/Users/shova/AppData/Local/Programs/Python/Python311/Scripts/pip
pip is /c/Users/shova/AppData/Local/Programs/Python/Python313/Scripts/pip
```

יש **שני** pip, בדיוק כמו ששני python. כל pip מתקין לתוך ה-Python שלו ולא לתוך האחר. ברגע שהסדר ב-PATH גורם ל-`pip` אחד לנצח ול-`python` השני לנצח, הותקנה חבילה לפרשן שלא רץ, ושתי הפקודות דיווחו הצלחה מלאה.

הבדיקה שחותכת את זה בשורה אחת:

```
python -m pip install <package>
```

`python -m pip` מריץ את ה-pip **של אותו** python שרץ עכשיו, ולכן ההתקנה והייבוא לא יכולים להתפצל. זו הסיבה שהצורה הזו מומלצת ולא סתם ארוכה יותר.

## טעויות נפוצות

1. **"הפקודה לא נמצאה, אז היא לא מותקנת"**. לפעמים היא מותקנת בתיקייה שאינה ב-PATH. `command not found` הוא דיווח על חיפוש שנכשל, לא על היעדר מהמחשב.

2. **"התקנתי גרסה חדשה ועדיין רצה הישנה, משהו נשבר"**. שלוש אפשרויות לפי הסדר: הישנה מוקדמת יותר ב-PATH, או שה-hash table עדיין זוכר את המיקום הישן ו-`hash -r` יפתור, או שיש alias שמכסה על שתיהן. `type -a` מבדיל ביניהן מיד.

3. **"`which` ו-`type` זה אותו דבר"**. `which` הוא לרוב תוכנית נפרדת שיודעת רק על קבצים ב-PATH. `type` הוא builtin שרואה גם aliases וגם builtins. `which cd` לא יעזור לך; `type cd` יגיד לך את האמת.

4. **"אפשר להוסיף נקודה ל-PATH לנוחות"**. אל תעשה זאת. משמעותו שכל תיקייה שתיכנס אליה יכולה לחטוף כל פקודה, וקובץ בשם `ls` בתוך ארכיון שהורדת ירוץ במקום `ls` האמיתי.

5. **"הסדר ב-PATH לא באמת משנה"**. הוא כל ההבדל בין הרצת 3.11 להרצת 3.13, כפי שנמדד למעלה על המכונה הזו.

## מתי זה לא משנה

כשמותקנת גרסה אחת בלבד של כל דבר, PATH הוא רקע שקוף שאף פעם לא תחשוב עליו. הוא הופך לקריטי ברגע שיש שתי גרסאות: שני Python, node גלובלי מול מקומי, כלי שהותקן גם דרך מנהל החבילות וגם ידנית. באותו רגע כל שאלה של "למה זה מתנהג אחרת אצלי" היא שאלה על סדר.

בסביבות מבודדות, כמו container או virtualenv, הבידוד עצמו נעשה בעיקר על ידי שינוי PATH. כלומר גם כשאתה בורח מהבעיה, אתה בורח באמצעות אותו מנגנון.
