# צינורות והפניה

הפקודות בשרשרת לא רצות אחת אחרי השנייה. הן רצות באותו רגע, ומי שלא יודע את זה כותב שרשרת שנתקעת ולא מבין למה.

## מה תדע בסוף

להסביר מה `|` מחבר בדיוק, למה שרשרת עם מיליון שורות יכולה להסתיים ברבע שנייה, ולמה קוד היציאה של שרשרת יכול להיות 0 גם כשהחוליה הראשונה נכשלה.

## האינטואיציה

שתי מכונות עותקים, והפעם מגש הפלט של הראשונה מוברג ישירות לחריץ הכניסה של השנייה.

שלושה דברים נובעים מהברגה הזו, וכולם מפתיעים בפעם הראשונה:

השתיים עובדות **במקביל**. השנייה מתחילה לטפל בדף הראשון בזמן שהראשונה עדיין מעתיקה את דף 500. אף אחת לא מחכה שהשנייה תסיים.

המגש בין השתיים **מוגבל**. אם השנייה איטית, המגש מתמלא, והראשונה נאלצת לעצור עד שיתפנה מקום. זה לא תקלה, זה מה שמונע מהראשונה להציף את הרצפה.

אם השנייה **הולכת באמצע**, אין למי להעביר. הראשונה מקבלת הודעה ונעצרת, גם אם נשארו לה עוד מיליון דפים.

## ההגדרות המדויקות

**Pipe, צינור**: `a | b` מחבר את stdout של `a` ל-stdin של `b`. ה-shell יוצר את שתי התוכניות יחד ומריץ אותן במקביל, כל אחת כתהליך נפרד. `|` לא מעביר את stderr, שממשיך ליעד שלו כרגיל.

**Pipe buffer, חוצץ הצינור**: אזור זיכרון שמערכת ההפעלה מחזיקה בין השניים, בגודל קבוע (64KB בלינוקס כברירת מחדל). הכותב ממשיך כל עוד יש מקום.

**Backpressure, לחץ חוזר**: כשהחוצץ מלא, הכתיבה של הצד השמאלי **נחסמת** עד שהצד הימני יקרא. כך שרשרת מווסתת את עצמה בלי שאף אחד תכנן זאת: הקצב נקבע על ידי החוליה האיטית ביותר.

**SIGPIPE**: כשהקורא סוגר את הקצה שלו והכותב מנסה לכתוב, מערכת ההפעלה שולחת לכותב את האות `SIGPIPE`, שברירת המחדל שלו היא לסיים את התהליך. זו הסיבה ש-`head` "עוצר" את מי שלפניו.

**קוד היציאה של שרשרת**: ב-bash, `$?` של `a | b` הוא הקוד של **החוליה האחרונה בלבד**. המערך `PIPESTATUS` מחזיק את כל הקודים, ו-`set -o pipefail` משנה את ההתנהגות כך שהשרשרת מחזירה את הכישלון הראשון.

## דוגמה מחושבת

שרשרת בת שלוש חוליות על ההיסטוריה של המאגר הזה:

```
git log --pretty=%s | grep "^unit:" | wc -l
```

```
2
```

`git log` כותב כותרת קומיט לכל שורה ל-stdout. `grep` קורא אותן כ-stdin, מעביר הלאה רק את מי שמתחילה ב-`unit:`. `wc -l` סופרת. אף אחת מהשלוש לא ידעה שהיא בשרשרת.

עכשיו ההוכחה שהן רצות במקביל:

```
time (seq 1 5000000 | head -3)
```

```
1
2
3

real    0m0.165s
```

`seq` התבקשה לייצר חמישה מיליון מספרים והשרשרת הסתיימה ב-165 אלפיות השנייה. אם `seq` הייתה מסיימת לפני ש-`head` מתחילה, זה היה לוקח הרבה יותר. מה שקרה: `head` קיבלה שלוש שורות, הדפיסה, סגרה את הקצה שלה, ו-`seq` קיבלה `SIGPIPE` ומתה אחרי כמה עשרות שורות.

## המקרה שמפיל את האינטואיציה

השרשרת נכשלה, ובכל זאת מדווחת הצלחה:

```
false | true
echo "exit: $?"
```

```
exit: 0
```

`false` תמיד מחזירה 1. ובכל זאת `$?` הוא 0, כי הוא מתאר רק את `true`, החוליה האחרונה. שתי הדרכים לראות את האמת:

```
false | true
echo "PIPESTATUS = ${PIPESTATUS[@]}"
```

```
PIPESTATUS = 1 0
```

```
set -o pipefail
false | true
echo "exit: $?"
```

```
exit: 1
```

זה בדיוק המקום שבו שלב ב-CI מדווח ירוק על build שנכשל: `build_something | tee build.log` מחזיר את קוד היציאה של `tee`, ו-`tee` כמעט תמיד מצליחה. בלי `pipefail` הכישלון נבלע.

## טעויות נפוצות

1. **"הפקודה הראשונה רצה, מסיימת, ואז השנייה מתחילה"**. לא. שתיהן רצות במקביל כתהליכים נפרדים. זו הסיבה ששרשרת יכולה להתחיל להדפיס תוצאות לפני שהקלט נגמר, וזו גם הסיבה שאפשר לשרשר קובץ לוג שעוד נכתב.

2. **"אם השרשרת החזירה 0, כל החוליות הצליחו"**. רק האחרונה. השתמש ב-`PIPESTATUS` או הפעל `set -o pipefail` בכל סקריפט שמשמעותי אם ייכשל.

3. **"`cat file | grep x` זה הניסוח הנכון"**. `grep x file` עושה אותו דבר בלי תהליך מיותר. ה-`cat` המיותר הזה נפוץ מספיק כדי שיהיה לו שם, Useless Use of Cat. זה לא אסון, אבל בראיון זה מסמן שלא הפנמת ש-`grep` יודעת לפתוח קובץ בעצמה.

4. **"אם השרשרת נתקעת, החוליה הראשונה תקועה"**. בדרך כלל ההפך: החוליה האיטית בהמשך מילאה את החוצץ, וה-backpressure עצר את הראשונה. תסתכל על מי שקורא, לא על מי שכותב.

5. **"`|` מעביר גם שגיאות"**. לא. stderr לא נכנס לצינור. אם אתה רוצה אותו בשרשרת, `a 2>&1 | b`.

## מתי זה לא משנה

בפקודה אינטראקטיבית קצרה על קובץ קטן, שום דבר מכל זה לא מורגש: הכל נגמר מיד, החוצץ אף פעם לא מתמלא, ואף אחד לא בודק קוד יציאה. ההבנה הזו מתחילה להשתלם בשלושה מקומות: סקריפטים ש-CI מריץ ושתוצאתם חייבת להיות אמינה, שרשראות על נתונים גדולים מהזיכרון, וכל מקרה שבו התהליך "נתקע" ואתה צריך לדעת באיזה קצה להסתכל.

לחלופין, כשהעיבוד באמת מורכב, כלי אחד שקורא ומעבד בעצמו יהיה קריא יותר משרשרת של שש חוליות. שרשרת היא כלי הרכבה, לא הישג.

## חיבור

הצינור הוא מה שהופך את שלושת הערוצים מ-`m0-streams` למערכת: בלי ההפרדה בין stdout ל-stderr, שרשרת הייתה מזהמת את הנתונים בהודעות שגיאה. `m0-pipes-drill` יתרגל את זה בידיים, ו-`m0-path-lookup` עונה על השאלה שהשרשרת מניחה בשקט: איך ה-shell בכלל מצא את `grep` ואת `wc` לפני שהריץ אותם.
