# פורטים ו-localhost: תרגול

כל תיאוריה על loopback נאמרה. עכשיו אתה מפעיל שרת, מכה בו מארבעה כיוונים שונים, ורואה מי מגיע ומי נחסם.

## מה תדע בסוף

להפעיל שרת ולדעת מה כתובת ה-binding שלו, לגלות בפקודה אחת אילו פורטים פתוחים, לחזות לפני ריצת `curl` אם החיבור יצליח, ולהסביר מה השתנה כשמחליפים את הכתובת.

## האינטואיציה

הבניין עדיין עומד. כל הניסויים כאן הם אותו ניסוי: מי עומד בדירה, ואיפה הוא מסכים לקבל מכתבים.

127.0.0.1 אומר "דירה שלי, בניין שלי בלבד". 0.0.0.0 אומר "דירה שלי, כל בניין שיגיע". השאלה בכל תרגיל: מאיפה הגענו, ואם המארח מסכים לפתוח לנו.

## ההגדרות המדויקות

**Binding address, כתובת האזנה**: הכתובת שעליה שרת בוחר לקבל חיבורים. קובעת מי בכלל יכול לדפוק בדלת. `127.0.0.1` פותחת רק לתנועה מקומית; `0.0.0.0` פותחת לכל הממשקים.

**`ss`**: כלי שורת פקודה לינוקסי שמציג חיבורי רשת ומאזינים פעילים. `ss -tlnp` מציג מאזיני TCP: t=TCP, l=listening, n=numbers not names, p=show process. בסביבות ישנות ייתכן ותראה `netstat -tlnp` במקום.

**`curl -v`**: curl עם verbose. מציג את שלבי ה-handshake ולא רק את קוד התגובה. כשאתה רוצה לראות אם השרת בכלל קיבל את החיבור, `curl -v` עדיף על `curl -s`.

## דוגמה מחושבת

הרץ כל תרגיל בסדר, קרא את הפלט, ורק אז עבר לשאלה שאחריו.

**תרגיל 1: האזנה על כל הממשקים.**

פתח טרמינל ראשון:
```
python3 -m http.server 9000
```

פתח טרמינל שני:
```
ss -tlnp | grep 9000
```

הפלט יראה שורה בסגנון:
```
LISTEN  0  128  0.0.0.0:9000  0.0.0.0:*
```

`0.0.0.0:9000` אומר שהשרת מוכן לקבל מכל כתובת. עכשיו נסה:
```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:9000
curl -s -o /dev/null -w "%{http_code}" http://localhost:9000
curl -s -o /dev/null -w "%{http_code}" http://[::1]:9000
```

שלושת הקריאות מחזירות `200`. `python3 -m http.server` ללא `--bind` מאזין על `0.0.0.0`, שכולל גם ממשק IPv4 וגם, בהגדרות רבות, IPv6.

**תרגיל 2: האזנה על IPv4 בלבד.**

עצור את השרת הקודם. הפעל עם binding מפורש:
```
python3 -m http.server 9001 --bind 127.0.0.1
```

בדוק עם ss:
```
ss -tlnp | grep 9001
```

הפלט:
```
LISTEN  0  128  127.0.0.1:9001  0.0.0.0:*
```

עכשיו נסה:
```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:9001
curl -s -o /dev/null -w "%{http_code}" http://[::1]:9001
```

הראשונה מחזירה `200`. השנייה מסתיימת בשגיאת חיבור (curl יציג `000` או `Connection refused`). השרת לא מאזין על ממשק IPv6.

**תרגיל 3: גילוי מאזינים על המכונה.**

```
ss -tlnp | grep LISTEN
```

בדוק אם אתה מזהה את השרתים שהפעלת. `ss` מציג גם את ה-PID של התהליך כשמריצים עם הרשאות מתאימות.

## המקרה שמפיל את האינטואיציה

מפעילים שרת ורואים בפלט: `Serving HTTP on :: port 9002`. מה `::` אומר?

`::` היא קיצור IPv6 ל-`0:0:0:0:0:0:0:0`, השקולה ל-`0.0.0.0` בעולם IPv6, כלומר "כל הממשקים בגרסת 6". על מערכת עם הגדרת dual-stack, `::` אכן מקבל חיבורים גם מ-127.0.0.1. על מערכות אחרות לא. לכן `http://127.0.0.1:9002` עשוי להצליח או להיכשל תלוי בהגדרות ה-OS, ולא בקוד.

כלל מעשי: בדוק תמיד עם `ss` לאחר ההפעלה לפני שאתה מניח שמשהו נגיש.

## טעויות נפוצות

1. **"נסיתי עם `curl localhost:9001` ועובד, אז השרת נגיש מכל מקום"**. `curl` מאותה מכונה תמיד יצליח ל-127.0.0.1. הבדיקה האמיתית היא מהתוכנה שצריכה להגיע, לא מאותה מחשב.

2. **"ראיתי `127.0.0.1:9000` ב-ss, הכל בסדר"**. כן, השרת רץ. אבל binding ל-127.0.0.1 אומר שאף מכונה חיצונית לא תגיע אליו, גם אם אין חומת אש.

3. **"הגדרתי `0.0.0.0` כדי לאפשר גישה, ועכשיו הכל מסודר"**. ייתכן, אם אין חומת אש בינך לבין האינטרנט. `0.0.0.0` בסביבה ללא firewall חושף את השרת לכל העולם. בענן security group מגן; בבית הנתב מגן; בפיתוח מקומי, בדוק לפני שאתה רץ עם `0.0.0.0`.

4. **"פורט 80 נדרש כדי שה-URL יעבוד"**. דפדפנים מניחים :80 ל-HTTP ו-:443 ל-HTTPS, אבל `curl` וכל לקוח API לא צריכים זאת. פורט 80 רלוונטי רק אם אתה רוצה URL נקי בדפדפן.

## מתי זה לא משנה

בתוך Docker compose, כאשר שירות פונה לשירות אחר על אותה רשת, binding address כמעט ולא משנה כי הם מדברים על רשת וירטואלית. מה שכן משנה שם הוא port mapping: `8080:8080` כשרוצים לחשוף לחוץ. בסביבה מנוהלת (Cloud Run, Railway, Fly.io), ה-binding תמיד על `0.0.0.0:$PORT` וה-platform קובע מה חשוף.

בראיון, "למה הביט לא עולה" לרוב מסתיים בתשובה אחת: bound to 127.0.0.1.

## חיבור
