# SSH: מפתחות מול סיסמאות

השאלה ששאלת בעצמך: מה SSH באמת אומר, ומה הוא החליף. התשובה לשאלה השנייה מסבירה למה הוא בנוי כמו שהוא בנוי.

## מה תדע בסוף

לפרוש את ראשי התיבות, להגיד מה SSH החליף ולמה, להסביר איזה קובץ הולך לשרת ואיזה לעולם לא, ולדעת את מי בדיוק מאמתת שאלת ה-fingerprint בהתחברות הראשונה.

## האינטואיציה

מנעול ומפתח, אבל בכיוון שאולי מפתיע.

אתה מייצר זוג: **מנעול** ו**מפתח**. את המנעול אתה מחלק בחופשיות, תולה אותו על כל דלת שתרצה להיכנס אליה, מצלם אותו, שולח אותו במייל. את המפתח אתה לא נותן לאף אחד לעולם.

כשאתה מגיע לדלת, אינך שולח את המפתח. הדלת מציגה לך אתגר, אתה פותר אותו עם המפתח שנשאר אצלך, ומחזיר את הפתרון. הדלת מוודאת שהפתרון מתאים למנעול שתלוי עליה. המפתח מעולם לא עזב את הכיס.

בסיסמה, לעומת זאת, אתה כן מוסר את הסוד עצמו בכל כניסה, ולמי שמחזיק בדלת יש עכשיו את הסוד המלא.

## ההגדרות המדויקות

**SSH, Secure Shell**: פרוטוקול להתחברות מוצפנת ומאומתת למכונה מרוחקת, ולהרצת פקודות עליה.

**מה הוא החליף**: לפני SSH השתמשו ב-**telnet**, **rlogin**, **rsh** ו-**FTP**. כולם העבירו את שם המשתמש והסיסמה **בטקסט גלוי** ברשת. כל מי שהיה על הדרך יכול היה לקרוא אותם. SSH לא הוסיף יכולת חדשה, הוא הוסיף הצפנה ואימות למה שכבר עשו. זה כל ההבדל, וזו הסיבה שהפרוטוקולים הישנים נחשבים היום שגיאת תצורה.

**Key pair, זוג מפתחות**: שני קבצים שנוצרים יחד.

- **Public key, מפתח ציבורי**, סיומת `.pub`: מיועד להפצה. נשמר בשרת בקובץ `~/.ssh/authorized_keys`.
- **Private key, מפתח פרטי**, בלי סיומת: אף פעם לא עוזב את המכונה שלך. אף פעם לא נשלח לשרת. אף פעם לא נכנס ל-git.

**Fingerprint, טביעת אצבע**: תקציר קצר של מפתח, כדי שאדם יוכל להשוות מפתח בלי לקרוא את כולו.

**known_hosts**: קובץ מקומי שבו נשמר מפתח השרת אחרי שאישרת אותו פעם ראשונה.

**TOFU, Trust On First Use**: מודל האמון של SSH. בפעם הראשונה אתה מתבקש לאשר את השרת ואין לך למה להשוות; מאותו רגע כל שינוי יתריע בקול.

## דוגמה מחושבת

יצירת זוג מפתחות והתבוננות בשניהם:

```
ssh -V
ssh-keygen -t ed25519 -f demo_key -N "" -C "demo@example"
ls
```

```
OpenSSH_9.7p1, OpenSSL 3.2.1 30 Jan 2024
demo_key
demo_key.pub
```

הציבורי, שורה אחת קריאה שאפשר להדביק לכל מקום:

```
cat demo_key.pub
```

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIE1je7xwBc4FLAUcSfEjt+A6VQGIWbn14hEHvYPXupCI demo@example
```

שלושה שדות: סוג המפתח, המפתח עצמו, ותגית חופשית לזיהוי. התגית היא הערה בלבד ואינה חלק מהאבטחה.

טביעת האצבע שלו:

```
ssh-keygen -l -f demo_key.pub
```

```
256 SHA256:WU3ODNC7FIcIZtiP/GUoiDKg8+lu7J/cxdDsg5BLQV0 demo@example (ED25519)
```

והפרטי נראה אחרת לגמרי. הרץ בעצמך:

```
head -c 60 demo_key
```

השורה הראשונה שתראה היא שורת פתיחה שכתוב בה, בין קווים מפרידים, שזוהי תחילת מפתח פרטי של OpenSSH, ואחריה גוש base64 ארוך. הטקסט המדויק אינו מודפס כאן בכוונה: השורה הזו היא בדיוק מה שסורקי סודות מחפשים במאגרי קוד, ואין סיבה לשתול אותה בקובץ לימוד.

וזה הלקוח המעשי: אם ראית את שורת הפתיחה הזו במקום שאינו המחשב שלך, בפרט ב-repository, בלוג או בהודעה, משהו השתבש וצריך להחליף את המפתח. הזוג בדוגמה נוצר בתיקייה זמנית לצורך ההדגמה בלבד ואינו משמש דבר.

## המקרה שמפיל את האינטואיציה

בהתחברות ראשונה מופיעה השאלה:

```
The authenticity of host 'example.com' can't be established.
ED25519 key fingerprint is SHA256:WU3ODNC7FIcIZtiP...
Are you sure you want to continue connecting (yes/no)?
```

כמעט כולם מקישים `yes` ומניחים שזה שלב באימות שלהם מול השרת. זה **ההפך**.

השאלה הזו מאמתת את **השרת מולך**. SSH שואל: המכונה שענתה בכתובת הזו מציגה את המפתח הזה. אין לך היסטוריה איתה, אז אין לי דרך לדעת אם זו באמת היא או מישהו שיושב באמצע ומתחזה. תחליט אתה.

כשתאשר, המפתח נשמר ב-`known_hosts`. אם בעתיד תופיע אזהרה חריפה על שינוי מפתח, המשמעות היא שהמכונה שעונה עכשיו אינה זו שאישרת. לפעמים זה שרת שהותקן מחדש באמת. לפעמים זו בדיוק ההתקפה שהמנגנון נועד לתפוס. זו הסיבה שמחיקת השורה מ-`known_hosts` כדי "שזה יעבוד" היא ההרגל המסוכן ביותר בנושא הזה.

האימות שלך מול השרת קורה בשלב אחר לגמרי, מול `authorized_keys`.

## טעויות נפוצות

1. **"שולחים את המפתח הפרטי לשרת"**. לעולם לא. לשרת הולך רק ה-`.pub`. אם הדבקת בטעות את הפרטי ב-`authorized_keys`, הדליפת את הסוד וגם זה לא יעבוד.

2. **"שאלת ה-fingerprint מאמתת אותי"**. היא מאמתת את השרת מולך. האימות שלך קורה מול `authorized_keys`.

3. **"SSH מצפין, אז הוא גם מאמת שאני מדבר עם הצד הנכון"**. הצפנה בלי אימות זהות מגינה מפני האזנה אבל לא מפני מישהו שיושב באמצע. `known_hosts` הוא החלק שמטפל בזה, ולכן דילוג עליו מוותר בדיוק על ההגנה הזו.

4. **"passphrase על המפתח זה כמו סיסמה לשרת"**. לא. ה-passphrase מצפין את המפתח הפרטי **על הדיסק שלך**. השרת לא יודע עליו כלום. הוא מגן על מקרה שבו הקובץ נגנב.

5. **"`.pub` הוא הסוד כי הוא קצר"**. ההפך הגמור. הציבורי נועד להפצה.

## מתי זה לא משנה

בהתחברות חד פעמית למכונה חד פעמית בסביבה מבודדת, סיסמה תעבוד ותסיים את העניין. מפתחות מתחילים להשתלם ברגע שיש יותר ממכונה אחת, יותר מאדם אחד, או אוטומציה: סקריפט לא יכול להקליד סיסמה, וזו הסיבה האמיתית ש-CI ו-git משתמשים במפתחות ולא בסיסמאות.

בראיון, השאלה על SSH היא כמעט תמיד שאלה על הכיוון: מה הולך לאן, ומי מאמת את מי.

## חיבור

SSH הוא הדוגמה הראשונה ביחידות האלה למנגנון שמפריד בין **הצפנה** לבין **אימות זהות**, וההפרדה הזו חוזרת בכל מקום: TLS עושה בדיוק את שני הדברים האלה עבור HTTPS, עם certificate במקום `known_hosts`. `m0-env-vars` ממשיך את השאלה איפה סודות באמת יושבים, ו-`m0-ports-localhost` מסביר לאן SSH בכלל מתחבר כשהוא פונה לפורט 22.
