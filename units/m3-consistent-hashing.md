# גיבוב עקבי
כשמוסיפים שרת לאשכול, consistent hashing מבטיחה שרק שבריר קטן של המפתחות עוברים בית.

## מה תדע בסוף
תוכל להסביר כיצד consistent hashing מחלקת מפתחות בין שרתים, לשרטט Hash Ring בידיים, ולנמק מדוע virtual nodes משפרים את האיזון.

## האינטואיציה
דמיין שעון עם מיליארד נקודות על היקפו. כל שרת תופס נקודה על השעון, וכל מפתח מקבל נקודה משלו. הכלל פשוט: כל מפתח שייך לשרת הראשון שמגיע אחריו בכיוון השעון (clockwise). כשמוסיפים שרת חדש, רק המפתחות שבין השרת החדש לקודמו עוברים בית; כל השאר נשארים בדיוק היכן שהיו.

## ההגדרות המדויקות

**Hash Ring, טבעת הגיבוב** הוא מרחב ערכים מעגלי מ-0 עד \(2^{32}-1\). פונקציית Hash כלשהי (בדרך כלל SHA-1 או MD5 עם modulo) מציבה גם שרתים וגם מפתחות על אותה טבעת.

**Consistent Hashing, גיבוב עקבי** הוא אלגוריתם חלוקה שמבטיח:
\[
\text{מפתחות שעוברים בית} \leq \frac{K}{N+1}
\]
כאשר \(K\) הוא מספר המפתחות הכולל ו-\(N\) מספר השרתים לפני ההוספה. כשמסירים שרת, עוברים לכל היותר \(\frac{K}{N}\) מפתחות.

**Virtual Node, צומת וירטואלי** הוא נקודה נוספת על הטבעת שמייצגת את אותו שרת פיזי. כל שרת מקבל בדרך כלל 100-200 virtual nodes. המטרה: לפזר עומס בצורה אחידה יותר, כי Hash function רגילה אינה מחלקת את הטבעת בשווה בין ה-N שרתים.

**Hotspot, נקודת חום** נוצרת כשאחד השרתים מקבל חלק לא פרופורציונלי של מפתחות בגלל פיזור לא אחיד על הטבעת.

## דוגמה מחושבת

נגדיר Hash Ring פשוטה מ-0 עד 99 (במציאות 0 עד \(2^{32}-1\)).

שרתים: A, B, C ממוקמים על הטבעת:

```
hash("ServerA") = 10
hash("ServerB") = 40
hash("ServerC") = 70
```

חלוקה: `0-9 → C`, `10-39 → A`, `40-69 → B`, `70-99 → C`

שלושה מפתחות:

```
hash("user:5001") = 55   →  שרת B
hash("user:5002") = 12   →  שרת A
hash("user:5003") = 82   →  שרת C
```

מוסיפים שרת D: `hash("ServerD") = 30`.

הטבעת החדשה: `10-29 → A`, `30-39 → D`, `40-69 → B`, `70-9 → C`

רק מפתחות בתחום 30-39 עוברים מ-A ל-D. המפתח user:5001 (55) נשאר ב-B ללא כל שינוי, user:5003 (82) נשאר ב-C. במספרים: `100 / (3+1) = 25` נקודות לכל היותר עברו, ובפועל עברו רק 10.

## המקרה שמפיל את האינטואיציה

עם שרתים פיזיים בלי virtual nodes, Hash function אינה מבטיחה שכל שרת יתפוס בדיוק \(\frac{1}{N}\) מהטבעת. בפרקטיקה, שרת אחד עשוי לשמור 60% מהמפתחות בעוד שניים אחרים חולקים את ה-40% הנותרים.

ניסויים מערכתיים הראו שעם 150 virtual nodes לשרת, ה-std.dev של הטעינה יורדת ל-5%-10% מהממוצע, לעומת עד 200% סטייה ללא vnodes. Apache Cassandra ו-Amazon Dynamo משתמשות בדיוק בטריק הזה.

## טעויות נפוצות

1. **"Consistent hashing מבטיחה חלוקה שווה בלי virtual nodes"** - שגוי. האלגוריתם מבטיח מינימום העברות בלבד. בלי virtual nodes ייתכן hotspot רציני שבו שרת אחד מקבל את עיקר העומס.

2. **"כשמוסיפים שרת, כל המפתחות מחולקים מחדש"** - שגוי. רק מפתחות בקטע הטבעת שבין השרת החדש לקודמו עוברים. כל שאר המפתחות לא נוגעים.

3. **"Hash Ring מתאימה רק ל-cache"** - שגוי. Apache Cassandra, Amazon Dynamo, Riak, ו-MinIO משתמשות בה לאחסון persistent עם repli.

4. **"מפתח תמיד הולך לשרת הגיאוגרפית הקרוב"** - שגוי. "קרוב" על הטבעת הוא ערך Hash, לא מרחק גיאוגרפי או רשת.

## מתי זה לא משנה

Consistent hashing מתאימה כשהאשכול גדל ומתכווץ לעיתים קרובות (auto-scaling, rolling updates, sharding אלסטי). אם האשכול סטטי לחלוטין, חלוקה פשוטה `key % N` פשוטה ומהירה יותר.

לשרתים שמטפלים בבקשות stateless (API gateways, עיבוד תמונות), round-robin או least-connections עדיפים כי אין חשיבות לאיזה שרת מגיעה כל בקשה.

בראיון: אם המראיין שואל על load balancer ל-stateless service, אל תציע consistent hashing. שמור אותה לאחסון מבוזר, caches, ו-databases שצריכות לדעת לאיזה node לפנות עבור מפתח נתון.

## חיבור

Consistent hashing היא אחד מלבני הבניין של distributed systems: היא מאפשרת ל-key-value store, לשרת ה-YouTube ול-URL shortener להפוך לאלסטיים. בלוק M3 בונה לאורכו את הפאזל: consistent hashing מאפשרת את `m3-key-value-store`, שמאפשרת את שאר ה-design interviews.
