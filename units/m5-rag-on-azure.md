# RAG על Azure

מי שמחבר חיפוש לבינה מלאכותית יודע ש-LLM לא זוכר את המסמכים שלך. RAG הוא הפיתרון הנפוץ ביותר.

## מה תדע בסוף

תדע לתאר את ארבעת שלבי RAG על Azure (אינדוקס, חיפוש, הרחבת הקשר, יצירה), להסביר את ההבדל בין חיפוש וקטורי, חיפוש מילות מפתח וחיפוש היברידי, ולזהות את שני המצבים שבהם RAG נכשל בעקביות.

## האינטואיציה

דמיין ספרייה של 10,000 עמודים עם מדריך טכני. אתה רוצה לשאול שאלה על מדיניות אחריות. אין טעם לקרוא את כל הספר, אז אתה פונה ל**ספרנית**: היא מוצאת את שלושת הדפים הרלוונטיים ביותר ומניחה אותם לפניך. עכשיו הקורא מסתכל רק על שלושת הדפים האלה ועונה.

RAG הוא אוטומציה של הספרנית הזו:

- **Azure AI Search** היא הספרנית, שמאחסנת ומאתרת קטעים.
- **Azure OpenAI** הוא הקורא, שמסכם ועונה על בסיס מה שמצאה הספרנית.
- **Chunk, קטע** הוא הדף שהיא מניחה לפניך.

האינטואיציה הזו נכונה לאורך כל היחידה: בכל שאלה, הספרנית פועלת לפני הקורא.

## ההגדרות המדויקות

**RAG, Retrieval-Augmented Generation (הרחבת הקשר בזמן ריצה)**: דפוס שבו שלב אחזור שולח שאילתה למסד ידע חיצוני ומחזיר קטעים רלוונטיים, שמוזרקים אל ה-prompt לפני שה-LLM מייצר תשובה. ה-LLM לא זוכר דבר בין שיחות, אך RAG נותן לו "דפים פתוחים" בכל פעם.

**Chunk, קטע מסמך**: מעבר קצר שנחתך מהמסמך המקורי, בדרך כלל 256 עד 512 טוקנים. זו יחידת האינדוקס הבסיסית. קטע ארוך מדי גורע ממדיוק הסריקה; קטע קצר מדי שוחק הקשר.

**Embedding, ייצוג וקטורי**: וקטור של מאות ממדים שמקודד את משמעות הטקסט. קטעים בעלי משמעות דומה קרובים מרחקית בחלל הוקטורי. מודל הטמעה (כגון `text-embedding-3-large`) ממיר כל קטע ואת השאילתה לוקטורים.

**Vector search, חיפוש וקטורי**: מוצא את K הקטעים שהוקטורים שלהם קרובים ביותר לוקטור השאילתה. Azure AI Search מממש זאת דרך HNSW (אלגוריתם גרף היררכי שמוגדר בעת יצירת האינדקס), שמאפשר חיפוש מהיר גם על מיליוני קטעים.

**BM25, חיפוש מילות מפתח**: אלגוריתם קלאסי שמדרג קטעים לפי תדירות המילים וייחודיותן בגוף המסמכים. חזק על מחרוזות מדויקות ושמות עצם ייחודיים; חלש על שאלות בשפה טבעית ורב-משמעות.

**Hybrid search, חיפוש היברידי**: מיזוג של תוצאות BM25 ו-vector search דרך Reciprocal Rank Fusion, קיצור: RRF. Azure AI Search מריץ את שני החיפושים במקביל ומשקלל את הדירוגים. בדרך כלל עולה על כל אחד בנפרד בשאלות בשפה טבעית.

**Semantic ranker, דורג סמנטי**: מודל cross-encoder שסורק את 50 תוצאות החיפוש המובילות ומדרג אותן מחדש לפי רלוונטיות עמוקה לשאילתה. מחייב SKU S1 ומעלה ב-Azure AI Search. עולה ב-latency אבל משפר דיוק.

**Grounding, עיגון**: כל טענה בתשובת ה-LLM ניתנת למעקב עד קטע מסמך ספציפי שהוחזר מהאינדקס. RAG ללא grounding הוא LLM שרץ עם דפים פתוחים אבל עדיין ממציא.

## דוגמה מחושבת

RAG על Azure מורכב משלושה שלבים: אינדוקס (פעם אחת), חיפוש ויצירה (בכל שאילתה).

**שלב 1: אינדוקס**

```
מסמך PDF
  --> פיצול לקטעים של 512 טוקנים
  --> הפעלת text-embedding-3-large על כל קטע
  --> שמירת (טקסט, וקטור, מטא-נתונים) ב-Azure AI Search index
```

Azure AI Search מקבל את הוקטורים עם הגדרת שדה `"type": "Collection(Edm.Single)"` ופרמטרי HNSW. מבחינת הספרייה: בניית הקטלוג.

**שלב 2: חיפוש**

```python
query = "מה תקופת האחריות על המוצר?"
query_vector = embedding_client.embed(query)

results = search_client.search(
    search_text=query,          # BM25
    vectors=[query_vector],     # vector search
    top=3,
    query_type="semantic",      # semantic ranker על ה-Top 50
)
context = "\n\n".join(r["content"] for r in results)
```

הספרנית רצה. היא מחזירה שלושה דפים.

**שלב 3: יצירה**

```python
system = (
    "ענה אך ורק על בסיס המסמכים הבאים. "
    "אם התשובה אינה במסמכים, אמור 'לא ידוע'.\n\n"
    f"{context}"
)
response = chat_client.complete(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": system},
        {"role": "user",   "content": query},
    ],
)
print(response.choices[0].message.content)
```

כל ציטוט בתשובה אמור להיות מאחד משלושת הקטעים. אם הוא לא, זו הזיה.

## המקרה שמפיל את האינטואיציה

האינטואיציה: "RAG פותר הזיות". בפועל, RAG מחליף הזיות מ*ידע לא קיים* בהזיות מ*הקשר לא מספיק*. הספרנית מחזירה רק שלושה דפים; אם התשובה מפוזרת על 40 דפים, ה-LLM לא יראה 37 מהם ועדיין יענה בביטחון.

שני מצבים שבהם RAG נכשל בעקביות:

1. **שאלות שליליות**: "האם המוצר אינו תומך ב-X?" - הretriever מוצא מסמכים עם X (כי הם הכי דומים), ה-LLM קורא שX כן קיים ועונה להיפך.
2. **שאלות צבירה**: "מהו הסיכום הכולל של כל ההזמנות?" - 3 קטעים לא יצמצמו מחשוב על כל האינדקס. לשאלות כאלה SQL על מסד נתונים בצד מתאים יותר.

## טעויות נפוצות

**חיפוש וקטורי בלי BM25**: וקטורים חלשים על שמות עצם ייחודיים וקודי מוצר. Hybrid search מוסיף BM25 כמעט ללא עלות נוספת.

**קטעים ארוכים מדי**: קטע של 2,000 טוקנים מכביד על מודל ה-embedding ועל semantic ranker. 512 טוקנים הוא נקודת מוצא טובה.

**בלי semantic ranker**: BM25 ו-vector מוצאים קטעים קרובים, לא בהכרח רלוונטיים. semantic ranker מדרג מחדש ומוריד שגיאות Top-K.

**prompt injection דרך מסמכים**: תוקף שמעלה מסמך עם הוראות כגון "התעלם מהכל ועשה X" יכול לשלוט ב-LLM אם לא מסננים. Prompt Shields ו-Content Filters ב-AI Foundry מגנים, אך רק אם מחוברים לצינור.

## מתי זה לא משנה

כשכל הידע הדרוש נכנס ל-context window של המודל (128K עד 1M טוקנים), שולחים הכל ב-prompt. מסמך בן 50 עמודים לא צריך RAG; קנה ידע של 50,000 עמודים כן. הtradeoff: context window שלם - עלות גבוהה ו-latency גבוה; RAG - עלות נמוכה אבל דיוק תלוי ב-retrieval.

בראיון: RAG הוא הכלי הנפוץ ביותר לשאלות "כיצד תחבר LLM למסד ידע קיים?". ציין hybrid search ו-grounding.
