# מאגר ארטיפקטים מול ניהול גרסאות

git שומר את מה שכתבת, מאגר ארטיפקטים שומר את מה שהבילד ייצר, ואלו שתי בעיות אחסון הפוכות שנפתרות בשני מבני נתונים שונים.

## מה תדע בסוף

להסביר במספרים מדודים למה קובץ בינארי ב-git עולה את מלוא הבתים שלו בכל גרסה ובכל clone, לבחור בין git, git LFS ומאגר ארטיפקטים לפי מה שנשמר, ולהצביע על השדה שמחבר commit מסוים לקובץ שרץ בפרודקשן.

## האינטואיציה

מפעל עם שני מבנים.

במבנה הראשון יושב ארכיון השרטוטים. כל שינוי בקו נרשם, אף דף לא נזרק, וכל מהנדס שמצטרף מקבל עותק מלא של הארכיון ביום הראשון. זה git.

במבנה השני יושב מחסן המוצרים המוגמרים. על כל ארגז יש ברקוד שנגזר מהתוכן עצמו, שני ארגזים עם תוכן זהה מקבלים אותו ברקוד ותופסים מקום אחד, לצד כל משלוח נשמרת תעודת משלוח שאומרת איזה שרטוט ואילו חלקים מספקים נכנסו לארגז, ומלאי ישן נזרק לפי מדיניות. זה מאגר ארטיפקטים.

הארכיון תוכנן כדי שכלום לא ייעלם. המחסן תוכנן כדי שכלום לא יאוחסן פעמיים ושמה שכבר לא נחוץ ייזרק. כשמכניסים בינארי לארכיון מקבלים ארכיון שתופס כמו מחסן, בלי אף אחת מהתכונות של מחסן.

## ההגדרות המדויקות

**Version control, ניהול גרסאות**: git הוא מאגר אובייקטים ממוען-תוכן. כל קובץ נשמר כ-blob, כל תיקייה כ-tree, כל נקודת זמן כ-commit, וכל אובייקט מזוהה ב-hash של תוכנו, היסטורית SHA-1 ובפורמט חדש יותר SHA-256. `clone` מביא כברירת מחדל את כל ההיסטוריה, לא את המצב הנוכחי בלבד. `--depth` מקצר את מה שהלקוח מוריד, אבל השרת עדיין מאחסן הכל ורוב ה-CI צריך היסטוריה כדי להשוות בין ענפים.

**Delta compression, דחיסת הפרשים**: git אורז אובייקטים דומים ב-packfile ושומר אחד מהם כהפרש מהשני. זה עובד כשהבתים דומים וכשהם עדיין לא דחוסים. פורמטים בינאריים נפוצים כמו jar, whl, zip, woff2, png ושכבת Docker כבר עברו דחיסה, ולכן הבתים שלהם קרובים לאקראיים, ההפרש בין שתי גרסאות גדול כמעט כמו הקובץ עצמו, ושתי הגרסאות משלמות מחיר מלא. זו הסיבה ההנדסית לפיצול, לא העדפת סגנון.

**Artifact, ארטיפקט**: תוצר הבילד. jar, wheel, tarball של npm, image של Docker, חבילת deb או rpm, או blob גנרי.

**Artifact repository, מאגר ארטיפקטים**: שרת שמנהל ארטיפקטים ומדבר את הפרוטוקול של כל אקוסיסטם. JFrog Artifactory הוא הדוגמה הנפוצה. יש בו שלושה סוגי repository: **local** למה שאתה מייצר, **remote** שהוא proxy ו-cache מול מקור חיצוני כמו Maven Central, npmjs, PyPI או Docker Hub, ו-**virtual** שמאחד local ו-remote מאחורי כתובת אחת כדי שהלקוח יגדיר מקור אחד בלבד.

**Checksum-based storage, אחסון לפי checksum**: כשמעלים קובץ, Artifactory מחשב את ה-checksum שלו, שומר את הבתים ב-filestore תחת שם שהוא ה-SHA-1, ורושם ב-database מיפוי בין הנתיב והשם שביקשת לבין אותו checksum. העלאה שנייה של אותם בתים מוסיפה שורה ב-database ולא קובץ. מכאן ש-copy ו-move הם פעולות database ולא העתקת בתים, ו-SHA-256 נשמר גם הוא כ-metadata.

**Coordinates, קואורדינטות**: הכתובת הלוגית של ארטיפקט. ב-Maven זה `group:artifact:version`, ב-npm זה `name@version`, ב-Docker זה `repository:tag` ובנוסף digest.

**Build-info**: קובץ JSON שה-CI מפרסם לצד הארטיפקטים. הוא רושם אילו modules נבנו, אילו ארטיפקטים יצאו ומה ה-checksum של כל אחד, אילו dependencies נצרכו ומה ה-checksum שלהן, משתני סביבה, ומקטע VCS עם ה-revision, ה-url וה-branch. זה החיבור בין git לבין הבינארי, ובלעדיו השאלה "איזה commit רץ עכשיו בפרודקשן" נענית בניחוש.

**Retention policy, מדיניות שמירה**: כלל שמוחק בילדים ישנים לפי גיל או לפי כמות. מחיקה כאן היא תפעול שגרתי. ב-git מחיקת בתים מההיסטוריה היא כתיבה מחדש של ההיסטוריה, כלומר שינוי כל ה-hash-ים מאותה נקודה והלאה.

אם \(b\) הוא גודל הארטיפקט ו-\(N\) מספר הגרסאות שנוצרו אי פעם, אז ב-git

\[
S_{\text{git}} = N \cdot b
\]

וכל clone משלם את הסכום הזה. במאגר ארטיפקטים, כאשר \(U\) הוא מספר קבוצות הבתים הייחודיות שעדיין בתוך חלון ה-retention,

\[
S_{\text{repo}} = U \cdot b, \qquad U \le N
\]

ואף לקוח לא משלם את הסכום, אלא רק את הגרסה שהוא מושך.

## דוגמה מחושבת

שני repositories, שלוש גרסאות בכל אחד, בדיוק 5,000,000 בתים לגרסה. בראשון תוכן טקסטואלי שמשתנה בשורה אחת בין גרסאות. בשני תוכן שכבר דחוס, כלומר בתים בעלי אנטרופיה גבוהה.

```
git init && git add src.txt && git commit -m v1   # ואז עוד שני commits עם שינוי שורה
git gc
git count-objects -vH | grep size-pack
size-pack: 641.32 KiB
```

```
git init && git add blob.bin && git commit -m v1   # ואז עוד שני commits עם תוכן חדש
git gc
git count-objects -vH | grep size-pack
size-pack: 14.31 MiB
```

שני המקרים הכניסו 15,000,000 בתים של תוכן. הטקסט נארז ל-641 KiB, יחס של פי 23 בערך, כי גם הדחיסה וגם ההפרשים עבדו. הבינארי נארז ל-14.31 MiB, שהם 15,000,000 בתים, כלומר יחס 1.00 ואפס רווח.

עכשיו בקנה מידה אמיתי. jar של 40 MB, 200 בילדים בשנה, שלוש שנים: ההיסטוריה מחזיקה כ-24 GB, כל clone מוריד אותם, וגם אחרי שהגרסה כבר לא רלוונטית הם נשארים. באותו תרחיש במאגר ארטיפקטים, אם 60 מהבילדים ייצרו בתים זהים הם נשמרים פעם אחת לפי ה-checksum, ומדיניות של 90 יום מגבילה את המצב היציב לחלון ולא לסכום מצטבר.

## המקרה שמפיל את האינטואיציה

האינטואיציה של הברקוד אומרת שהכתובת מזהה את הבתים. היא לא.

`myapp:1.4.2` ב-registry של Docker הוא מצביע שניתן לשנות. אפשר לדחוף שוב את אותו tag על תוכן אחר, והוא יצביע מעכשיו ל-digest אחר. לכן המשפט "העלינו לפרודקשן את 1.4.2" אינו אמירה על בתים, אלא אם נעשה pin ל-digest בצורה `myapp@sha256:...`. אותו דבר ב-Maven: גרסת `-SNAPSHOT` מיועדת לדריסה, וגרסת release אמורה להיות מוגדרת כלא ניתנת לדריסה במאגר, אבל זו הגדרה שמישהו צריך לבצע.

**Digest**: ה-hash של התוכן עצמו. הוא המזהה היחיד שאי אפשר לכוון מחדש. זו הסיבה ש-build-info רושם checksums ולא רק מספרי גרסה.

## טעויות נפוצות

1. **"git LFS פותר את הבעיה, אז אפשר להישאר ב-git"**. LFS מוציא את הבתים לאחסון נפרד ומשאיר ב-git קובץ מצביע, ולכן עלות ה-clone באמת יורדת. אבל לא קיבלת פרוטוקול registry שהלקוחות הרגילים יודעים לדבר, לא proxy למקורות חיצוניים, לא מדיניות retention לכל חבילה, ולא build-info. בנית מאגר ארטיפקטים חלש יותר.

2. **"tag מזהה גרסה, אז הוא מזהה בתים"**. לא. tag הוא שם שניתן לכוון מחדש. רק ה-digest או ה-checksum נגזרים מהתוכן.

3. **"תמיד אפשר לבנות מחדש מה-commit, אז אין טעם לשמור את הבינארי"**. בנייה חוזרת מאותו commit לא מבטיחה את אותם בתים: חותמות זמן שנצרבות בקובץ, טווחי גרסאות של dependencies שנפתרים אחרת היום, גרסת toolchain, ומשתני סביבה. reproducible build הוא הישג הנדסי, לא ברירת מחדל. בדיוק לכן build-info רושם את ה-checksum שיצא בפועל.

4. **"מאגר ארטיפקטים הוא bucket של קבצים"**. bucket מגיש בתים. מאגר ארטיפקטים מדבר את פרוטוקול האקוסיסטם, כלומר layout של Maven, ה-registry API של npm, ה-simple index של PyPI ו-registry v2 של Docker, ומגיש גם את ה-metadata וה-index שהלקוחות האלה דורשים. לכן `pip install` ו-`docker pull` עובדים מולו בלי שינוי בקוד.

5. **"remote repository הוא גיבוי של המקור החיצוני"**. remote הוא cache. הוא מגן מפני נפילה או הסרה של חבילה מלמעלה כל עוד היא כבר נמשכה ונשמרה, אבל מה שאתה ייצרת יושב ב-local, ורק הוא באחריותך לגבות.

## מתי זה לא משנה

כשאין בילד, אין צרכן שני, ואין צמיחה מדידה של ההיסטוריה. הפרויקט הזה הוא בדיוק המקרה: `vendor/` מחזיק 676 KB בתוך git, מתוכם 304 KB הם 20 קבצי woff2, כלומר בינאריים דחוסים, והם נכתבו פעם אחת ולא משתנים. מאגר ארטיפקטים כאן היה עלות תפעולית נטו.

ההחלטה מתהפכת כשמופיע אחד מאלה: יותר מצרכן אחד לבינארי, סיכון זמינות או רישוי במקור החיצוני, דרישת provenance או סריקת אבטחה, או היסטוריה שגדלה בגיגה-בתים. בראיון, השאלה "למה לא פשוט לעשות commit ל-jar" בודקת אם אתה יודע שהעלות מצטברת על פני ההיסטוריה ומוכפלת במספר ה-clones, ולא עלות דיסק חד פעמית.
