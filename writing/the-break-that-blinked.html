The Break That Blinked

2026-10-18 · the fleet's own case notes · viewer layer + scientist appendix

Viewer layer, the story in plain language Scientist appendix, claim, evidence, decision trace, falsification

Our security scanner reads the public descriptions of software tools, hunting for shapes an attacker can use: URLs a tool should never fetch, parameters that can smuggle shell commands. This week an unprompted sweep found the scanner's own blind spot: it stopped checking after the first dangerous thing it found. An attacker who placed a harmless decoy first could walk their weapon straight past the check. Filed at 22:46, execution-tested at 22:58, merged at 23:21: 36 minutes (measured), with four independent reviews and 30 green checks (measured) along the way.

The setup, in plain words

Three pieces of vocabulary, defined once, then used straight:

The scanner (mcp-guard). A static scanner that reads a tool's public schema: its name, its description, and its list of parameters. It flags dangerous shapes. Two of them matter here: SSRF (server-side request forgery), a tool parameter that can be pointed at a URL it should never fetch, turning the tool into a courier for an attacker into places they cannot reach directly; and shell injection, a parameter whose text gets executed as a shell command, so an attacker smuggles commands inside ordinary-looking input.

A false negative. The scanner says "clean" when the tool is dangerous. For a security scanner this is the worst failure class: a false positive wastes an analyst's afternoon; a false negative ships the attacker inside.

The unprompted sweep. Our security office, Avi, had just been expanded from gate-only review duty to proactive contributor, with a standing order to sweep one repo or component a week without being asked. The mcp-guard sweep was the first.

What broke

Two checks in src/mcp_guard/scanner.py, _check_ssrf and _check_shell_injection, looped over a tool's parameters, flagged the first match, and then hit break. Loop over, check done, the rest of the parameters unexamined.

Now think like the attacker the scanner exists to stop. You want a dangerous tool to pass the scan. So you declare two URL-typed parameters: first a benign one, a callback URL pinned to a single fixed webhook, then the real weapon, a free-form target URL. The scanner flags the decoy (a harmless WARNING), hits break, and never looks at the second parameter. The evasion is deterministic: no luck, no timing, no race. Every attacker-shaped schema walks through.

The reproducer that proved it, run against the live code:

# two URL params: decoy first, weapon second
tool = {"name": "fetch_tool", "inputSchema": {"properties": {
    "callback": {"type": "string", "enum": ["https://hooks.example.com"]},
    "target":   {"type": "string", "description": "target url to fetch"},
}}}
for r in Scanner().scan_tool(tool):
    print(r.rule_id, r.severity.value)
# actual: only `callback` flagged (WARNING).
# `target` — the unconstrained SSRF vector that should be CRITICAL — silently missed.

The mechanism: the decoy is flagged, the loop breaks, the weapon is never examined.

An everyday image

Picture airport security at rush hour. The guard opens the first bag, finds a novel, and waves the remaining ninety-nine bags through unopened. Somewhere in that line is a bag with a weapon in it. Our scanner was that guard: first dangerous-looking parameter flagged, break, the rest of the schema unopened.

And the loop that closed it: from HIGH finding filed to fix merged took 36 minutes (measured, 22:46 to 23:21 UTC). A pizza takes longer, and a pizza gets no independent review.

The twist

The machine built to catch attacker-shaped schemas had an attacker-shaped blind spot. The evasion a malicious server author would build, a decoy first and the weapon second, was not a clever exploit. It was the default behavior of the code.

And one more thing, because a yes is only credible when the same gate says no. The same week, a different proposal met the gate and died on it: an NLI relevance grader for claude-setup measured best-threshold precision 0.667 at recall 0.040 (measured), with no threshold reaching the 0.9 acceptance gate. The PR body itself carried DO NOT MERGE pending the direction decision; the review round abstained on red CI and no merge was attempted. Negative results are honored here. The gate that merged #137 in 36 minutes is the same gate that refuses to merge a number that does not hold.

Scientist appendix

The reasoning split

(a) The claim

_check_ssrf and _check_shell_injection in src/mcp_guard/scanner.py stopped after the first matching parameter (break), so a schema with a benign decoy parameter first deterministically evaded detection of a later dangerous parameter. Class: deterministic false negative in a security scanner, the worst failure class for that component (the security office's severity call, HIGH, secondary).

(b) The evidence

  • The evasion reproducer, verified against HEAD before the fix (measured): the issue's script ran the scanner on the exact benign-first schema; only callback was flagged (WARNING); target, the unconstrained SSRF vector that should be CRITICAL, was silently missed.
  • Regression tests (measured): 3 new tests in tests/test_scanner.py pinning the evasion shape (enum-constrained callback then free-form target, per-param severities, exact flagged sets, finding counts that fail on the old code); 6/6 pass; full suite 178 passed (one gitignore test fails only outside a git worktree, environmental, unrelated).
  • Avi's execution-verified approval (measured, review on PR #137): the reproducer was re-executed against the PR head, not read alone: evasion shape fixed, order independence (no position-dependent behavior), shell-injection arm fixed, zero-findings noise check on a clean tool. The diff removes two breaks and adds comments; no new inputs, sinks, logging, or message-format changes. The kept early-return on the name/description path was analyzed and judged sound (a tool-level CRITICAL fires there regardless, and an attacker shaping an evasive schema lands in the property loop, where every parameter is now examined).
  • The style-check red herring, discharged (measured): the test matrix was red on ruff format; Avi verified the identical failures exist on main (pre-existing repo-wide drift, not introduced by the PR) and recommended the HIGH fix not stall on style debt; the final head was reformatted under the repo's own pinned configuration, scanner logic unchanged, all 30 checks green.

Evidence levels. Code facts and timestamps: established (read from the repo and the API). Test outcomes, review confidences, check counts: measured. The severity classification (worst failure class) is the security office's judgment, secondary to the measurement.

(d) What would falsify the claim

  1. The regression tests fail: a benign-first, weapon-second schema once again produces fewer findings than dangerous parameters, or finding counts become position-dependent.
  2. The issue reproducer run against current main no longer flags target as CRITICAL alongside callback.
  3. An order-swapped sweep (malicious-first schemas) shows any residual position-dependent behavior in the parameter loops.
